# Spec-authoring guide — FSL model rebuild (project blocks)

Every project block of the v29 model is re-expressed as a Python **SPEC** dict in `model/fsl/specs/<module>.py`.
The framework (`model/fsl/project.py`) turns a spec into three sheets — `<ID> <Code> Input`, `<ID> <Code> Calc`,
`<ID> <Code> Output` — and standardises capex/depreciation, working capital, the project P&L, FCFF and returns.
The verification harness rebuilds Global Inputs + the project (+ its `depends`) as a mini workbook, recalculates it
with LibreOffice and compares Revenue / Cost of sales / Opex / D&A / EBIT with the v29 `Output_Standalone (IDR)` block,
year by year FY2024-FY2036, to 0.001 IDR bn.

```
cd /home/user/fks-danantara-deck.
python3 model/verify/verify_block.py <ID>            # dep_method=1 (v29 depreciation method) is the default for verification
```
`RESULT: PASS` is required for every block. The harness prints per-year diffs for lines that do not match.

## Source material (do not modify)
* `model/source/V29_Ruby_FM_Danantara.xlsm` — the v29 workbook (read-only).
* `model/inspect/v29/<Sheet>__formulas.tsv` / `__values.tsv` — grid dumps (row number in column 1, then columns A, B, C ...).
  `__cells.txt` — one line per non-empty cell: `A1<TAB>formula<TAB>cached value`.
  Key sheets: `Calculation_FSL`, `Calculation_SOEs`, `Input`, `Output_Standalone_IDR_`, `Output_FSL`, `Return_New_Assumption`, `Sheet3`.
* Column-to-year mapping in v29: `Input` K..W = 2024..2036 (J = 2023 / base); `Calculation_FSL`, `Calculation_SOEs` I = 2023, J..V = 2024..2036;
  `Output_Standalone (IDR)`, `Output_FSL` J..V = 2024..2036 (I = totals or opening).
* v29 scenario selectors: `Input!G4 = 1`; every `INDEX(...,$Gnnn,0)` row selects its first "Baseline" row, except `Input!G492 = 2`
  (Ciwandan ASP: second row) and `Input!G1241 = 2` (Ciwandan use of fund). Always use the **effective** values shown in the
  `__values.tsv` dump of the selector row (K..W), not the raw baseline rows, and cite the selector row (e.g. `Input!K445:W445`).
* Named constants in v29 formulas: `USD_IDR` = Calculation_FSL!F17 = 16,265; `Billion` = 1e9; `Million` = 1e6; `Thousands` = 1e3; `Month_Year` = 12.
* v29's model-period flag `J$12` (row 12 of Calculation_FSL) is 1 for 2024-2036 — use `{flag}` in templates.

## Model column layout (all time-series sheets)
A spacer | B label | C unit | D type | E scalar-or-total | **F = 2023 (opening / pre-2024), G = 2024 ... S = 2036** | T source | U note.
Header rows: 5 Year, 6 Period end, 7 Days, 8 Forecast flag (1 for 2024-2036, 0 for 2023). Data from row 10.

## SPEC schema
```python
SPEC = {
  "id": "P05", "code": "Dumai", "name": "Dumai bagging & weighbridge", "short": "Dumai",
  "entity": "...", "entity_short": "...", "category": "Planned project" | "Existing business" | "Committed project" | "BUMN synergy" | "Pipeline",
  "description": "one sentence on the business and how revenue/costs are driven",
  "v29": {"calc": "Calculation_FSL rows a-b", "input": "Input rows c-d", "standalone": "Output_Standalone (IDR) rows e-f", "flag": "Output_FSL!Fnn (= 1)"},
  "v29_rows": {"rev": <row of Net Sales in Output_Standalone (IDR)>, "cogs": .., "opex": .., "da": .., "ebit": .., "fin": .., "tax": .., "np": ..},
  "defaults": {"in_valuation": 1, "case": 1, "econ_interest": 1.0},   # case 1 = both company cases, 2 = With-BUMN case only
  "existing": False,             # True for existing businesses (no entry cost; Dec-23 receivables allocated)
  "depends": ["E2"],             # other project IDs referenced with {x:ID:key}
  "commissioning": {"year": 2026, "source": "Calculation_FSL!F170", "cls": "v29", "note": "..."},   # None for existing businesses
  "capex": {"total_usd": 6.8095, "source": "...", "pct": {2026: 1.0}, "pct_source": "...", "building_share": 0.6, "building_source": "...",
            "life_b": 20, "life_e": 8, "lives_source": "...", "hist_confirmed": 0, "note": "..."},   # or None when the block has no capex
  "inputs": [ ... ],             # see helpers.annual / helpers.scalar
  "calc":   [ ... ],             # see helpers.row and the generators
  "hooks": {"revenue": "<calc key>", "cogs": "<calc key or None>", "opex": "<calc key or None>", "da_other": "<calc key or None>", "other_income": None},
}
```
* `hooks.revenue/cogs/opex` are **positive** IDR bn amounts (the Output sheet applies the signs). `hooks.da_other` = depreciation of
  existing assets / G&A depreciation etc. (positive), added to the framework's depreciation on project capex.
* `capex.pct` shares are of **total** capex; the 2023 key is the pre-2024 (sunk) spend. Shares must add to 1.0.
  v29 timing comes from `Calculation_FSL` rows 1474-1481 (USD m by year; column I = pre-2024) and the `Input` capex rows they reference.
* Depreciation of project capex is generated by the framework from `capex` (method 1 = v29: total capex x share / life x operating flag).
  Do **not** re-model it in `calc` — but do model existing-asset depreciation, G&A depreciation, and any v29 depreciation that
  is NOT tied to the capex module (e.g. DMS equipment that v29 depreciates without any capex cash flow — see the block briefs).
* Working capital is generated by the framework (Global AR/AP days). Do not model it in `calc`.
* Financing cost rows of v29 blocks (Cigading existing / Wharf 2) are **corporate** in the revised model: do not put them in the spec.
* Tax: the framework taxes MAX(0, project EBIT) at the global rate (v29 line method).

## Input rows (`helpers.annual`, `helpers.scalar`)
```python
annual(key, label, unit, values_dict_by_year, source, cls="v29", section="...", note=None, fmt=None)
scalar(key, label, unit, value, source, cls="v29", section="...", note=None, fmt=None)
const(v, first=None)      # {2024..2036: v}, optionally a different 2024 value
```
* `cls`: "v29" (value taken from v29), "DERIVED", "UPDATED" (user-supplied information), "CHANGE" (user-requested change),
  "DUMMY" (Badas only), "PROV" (provisional), "CONTROL".
* Every annual assumption must have one editable value per year (write the effective v29 value into every year, even if constant).
* `source` must cite the exact v29 cells (sheet!range). Put v29 quirks in `note` (e.g. "v29 overrides Input!J209 with a typed 1.1 m t").
* Units: t, IDR/t, IDR bn, USD m, %, index, flag, year, x, days, sqm, IDR/t/month, IDR/sqm/month, months, persons.

## Calc rows (`helpers.row` and generators)
```python
row(key, label, unit, f, section, f0=None, fmt=None, total=False, bold=False, link=False, note=None)
growth_index(key, label, growth_in, section)                       # 1.00 in 2023, then prev x (1 + growth) x flag
fixed_cost(key, label, base_in, growth_in, section)                # -> [key_idx, key]: cost = base x index
per_ton_cost(key, label, base_cost_in, base_vol_in, growth_in, volume_c, section, uplift=None)   # -> [key_cost_t0, key_idx, key_cost_t, key]
sum_rows(key, label, [keys], section)
```
Formula templates are Excel formulas with tokens:
* `{in:key}` input row (annual: same year column; scalar: its cell), `{in:key@2025}` a fixed year.
* `{c:key}` calc row same column, `{c:key@prev}` previous column, `{c:key@2025}`, `{c:key@all}` = range F..S, `{c:key@cum}` = SUM($F..current).
* `{x:E2:key}` another project's calc row (same column); `{xin:P01:key}` another project's input row. Add the ID to `depends`.
* `{g:key}` Global Inputs: `fx`, `tax_rate`, `ar_days`, `ap_days`, `year`, `dcf_flag`, `val_year`, `dep_method` ...
* `{y}` year header cell of this column, `{yprev}`, `{days}`, `{flag}` (forecast flag = v29 J$12).
* Framework calc keys available in every project: `opflag` (1 from commissioning year; = flag for existing), `capex_usd`, `capex_idr`,
  `capex_cum`, `dep_new`, `nbv_new`, `da_total`, `ar`, `ap`, `nwc`, `dnwc`.
* Use `f0` for the 2023 column when it differs (e.g. `"=1"` for an index, `"=0"` for a flow). Without `f0` the same template is
  written in the 2023 column too (fine for rows that are naturally 0 there because `{flag}` = 0).
* Keep IDR bn as the unit for money rows: `... /10^9` for IDR, `x {g:fx}/1000` for USD m -> IDR bn.
* Make every row transparent: one driver per row, labels that explain the formula ("Revenue = volume x tariff / 1e9").

## Conventions for reproducing v29
* Indices: v29 starts at 1 in the 2023 column and multiplies by (1 + growth of the year) from 2024 — `growth_index` does exactly this.
* Per-ton costs: cost/t (2023) = FY2023 cost / FY2023 volume x 1e9 [x uplift where v29 applies 120%], grown by an index, x volume of the year.
* Operating-flag blocks: revenue etc. x `{c:opflag}` where v29 multiplies by its "Operation Period" row.
* Where v29 hard-codes a number inside a formula (e.g. `*0+1100000`, `0.005` insurance), expose it as an input with cls "v29" and cite the cell.
* Where v29 has a formula break (broken/empty reference), reproduce the **effective** behaviour so the harness passes, and document
  the break in the input `note` and in the module docstring ("v29 source issue"). Do NOT silently fix it — the company-level
  reconciliation reports v29 issues separately.
* The module docstring must summarise the effective v29 logic (as in `e2_cigadingExisting.py` / `p02_cigConveyor.py`).

## Worked examples
* New project with cross-project links: `model/fsl/specs/p02_cigConveyor.py`, `p01_cigWharf2.py`.
* Existing business with many cost lines: `model/fsl/specs/e2_cigadingExisting.py`, `e1_telukLamong.py`.
After the spec passes, also run it with `--dep-method 2` once to confirm it still recalculates without formula errors (differences vs v29
are expected with method 2 and are not a failure).
